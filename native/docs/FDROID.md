| Generated by | `scripts/publish-fdroid.sh` |

The repository is a static directory of a signed index plus the APK, served by
GitHub Pages. F-Droid clients verify the index against the repo key, then verify
the APK against the signer allowed in the metadata.

The APK is the same artifact as the GitHub release. Android upgrades an installed
BEUConnect in place because both carry the release key; the debug-signed
development builds install only after an uninstall.

## 2. Keys

Two independent keys. Do not merge them.

| Key | Signs | Path |
|---|---|---|
| Release key | the APK | `~/.config/beuconnect/beuconnect-release.jks`, secrets in `signing.env` |
| Repo key | the index, `entry.jar` | `~/.config/beuconnect/fdroid-repo.jks`, alias `fdroidrepo` |

`fdroid-signing.env` holds `FDROID_KEYSTORE`, `FDROID_KEY_ALIAS`,
`FDROID_KEY_PASS` and `FDROID_KEY_DNAME`; the publish script reads it and writes
a mode-600 `config.yml` in a scratch directory. Neither file is in this
repository. Back both up offline — losing the repo key forces every client to
remove and re-add the repository, losing the release key blocks every future
update.

`entry.jar` is signed SHA-256/SHA-384. `index-v1.jar` carries a SHA-1 signature
because fdroidserver keeps the legacy index for old clients; that is by design,
not a defect to fix.

## 3. Publishing a release

```sh
# 1. version: nsh.json `version` and `build`, then a changelog entry
$EDITOR nsh.json
$EDITOR fastlane/metadata/android/en-US/changelogs/<build>.txt

# 2. release: checks, tests, the slim arm64 APK, size gate, verification
./scripts/release.sh

# 3. publish the APK as a GitHub release, then build the repo index
gh release create "v$(bun -e 'console.log(require("./nsh.json").version)')" \
  dist/BEUConnect-*.apk#BEUConnect.apk --notes-file /tmp/notes.md
./scripts/publish-fdroid.sh v1.2.0 ../beuconnect-fdroid
git -C ../beuconnect-fdroid commit -am "BEUConnect 1.2.0" && git -C ../beuconnect-fdroid push
```

`publish-fdroid.sh` downloads the release APK, refuses it unless `apksigner`
reports the signer in `fdroid/metadata/org.beuconnect.app.yml`
(`AllowedAPKSigningKeys`), runs `fdroid update --clean`, restores the repository
icon that `--clean` replaces with a placeholder, and writes `../beuconnect-fdroid/repo`.

GitHub Pages rebuilds within a minute; the index URL is
`repo/index-v2.json` (also `index-v1.jar`, `entry.jar`, `index-v1.json`).

## 4. Installing

In the F-Droid client: **Settings → Repositories → Add repository**, then the URL
above. The client fetches the index, shows the fingerprint, and offers BEUConnect
1.1.0. The landing page also carries an `fdroidrepos://` link that opens the
client directly.

Without F-Droid, the APK at `repo/org.beuconnect.app_2.apk` installs the same way
as the GitHub release asset.

## 5. Official F-Droid: building without the nsh tarball

fdroiddata builds every app inside a Debian container that has no network, from a
recipe in the metadata `Builds:` block, and may only use binary dependencies that
come from a trusted build (Debian, Maven Central, and similar) or that the recipe
builds itself.

BEUConnect is a NativeShell app, and that is the whole difficulty. Its Android
host is assembled from two artefacts of `longbridge/nsh` (Apache-2.0, tag
`v0.3.0`): the `nsh` CLI that bundles `App.tsx` into `assets/nsh/`, and the
Android runtime — `libnsh.so` plus `classes.jar` — that the rest of the APK is
compiled against. The installer puts both in `~/.nsh`, as binaries from a release
tarball, which is not a trusted binary source.

Both have source, so `scripts/build-nsh-from-source.sh` builds them:

```sh
git clone --depth 1 --branch v0.3.0 https://github.com/longbridge/nsh ../nsh
NSH_SRC=../nsh ./scripts/build-nsh-from-source.sh arm64-v8a
```

It runs `cargo build --release -p nsh-cli`, then `cargo xtask android --release`
for `libnsh.so` and the runtime's Java classes, packs the same `nsh.aar` that
`cargo xtask dist` would, and hands the result to `build-android-host.sh` through
`PATH` and `NSH_AAR`. `SIGN=0` stops at the aligned APK, so the caller can put
its own key on it. Nothing in that path is a prebuilt binary; the bundler is
`rolldown` and `oxc`, both Rust, so no Bun or Node is involved either.

What the recipe still needs on top of that:

| Piece | Why |
|---|---|
| A pinned Rust toolchain | Debian trixie ships 1.85; `nsh` builds on 1.99. `sudo:` installs rustup to `/opt/rust` and the build exports `RUSTUP_TOOLCHAIN`, so the `stable` in nsh's `rust-toolchain.toml` does not trigger a second download. |
| ~700 crates from crates.io | `prebuild:` runs `cargo fetch --locked` into `CARGO_HOME`, which is outside the source tree, so nothing it downloads reaches the scanner. |
| libclang | `quickjs-jit-sys` runs `bindgen` at build time, and `bindgen` loads `libclang`, which the build-server image does not carry. `sudo:` installs `libclang-dev` and `build:` exports `LIBCLANG_PATH`. |
| SDK platform 35 and build-tools 35 | `cargo xtask android` compiles the runtime's Java with `javac --release 17` against `platforms/android-35/android.jar`, and the app's own aapt2/javac pass needs a platform too. The image ships no platform, and its `d8` is 31.0.0, which predates Java 17 class files, so `prebuild:` installs `platforms;android-35` and `build-tools;35.0.0` with `sdkmanager`. |
| Its own signing key | F-Droid signs what it builds. See §5.1. |

`fdroid/fdroiddata/org.beuconnect.app.yml` is the recipe, and it builds `v1.1.3`
on F-Droid's build server: every job in merge request
<https://gitlab.com/fdroid/fdroiddata/-/merge_requests/54557> passes, `fdroid
build` included, which compiles the `nsh` CLI, `libnsh.so` and the runtime's
Java classes from the srclib before it compiles the app. `v1.1.2` did not build
there — its host script demanded a keystore in a `SIGN=0` build, which a server
that signs nothing has no reason to carry, and 1.1.3 moves that check into the
signing branch. Until the merge request is merged, the self-hosted repository
above is the only F-Droid channel.

### 5.1 Two installs, two keys

F-Droid builds and signs with F-Droid's key, so a device that installed
BEUConnect from the GitHub release or the self-hosted repository cannot update
into the F-Droid build, and vice versa: Android refuses an update signed by a
different key. Adding both repositories to one client produces two unrelated
entries, and switching between them is an uninstall and a reinstall, which takes
the on-device planner and attendance data with it.

The self-hosted repository exists so that there is a channel that upgrades in
place. Turning on the official one does not replace it.

`Binaries:` would avoid all of that by letting F-Droid publish the upstream-signed
APK after verifying it against its own build. That needs the build to be
reproducible, and it is not — though only just. The APKs themselves agree: of 32
entries, 31 are byte-identical (`AndroidManifest.xml`, `resources.arsc`,
`classes.dex` and every asset); only `lib/arm64-v8a/libnsh.so` differs. The crate
paths are not the reason either: `libnsh.so` carries 638 absolute
`…/.cargo/registry/…` and build-directory strings, `--remap-path-prefix` (rustc)
and `-ffile-prefix-map` (the QuickJS C files) remove all of them, and the binary
still differs — from a build in another directory, and from a second build in the
same one. 37 to 45 of 43,689 symbols move between builds, all `rquickjs`
`___impl_*` instantiations alongside `lld`'s `__CortexA53843419_*` errata stubs,
with a few hundred bytes of `.text` and `.eh_frame`. That is nondeterminism in
nsh's own build (fat LTO, `codegen-units = 1`), not a flag this repository can
set, so `Binaries:` stays out until nsh produces the same bytes twice.
