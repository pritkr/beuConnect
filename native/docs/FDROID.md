# F-Droid

BEUConnect ships through two F-Droid paths. One is live, the other is blocked on
a dependency that is not built from source.

| Path | Status | Where |
|---|---|---|
| Self-hosted repository | Live since 2026-10-28 | <https://pritkr.github.io/beuconnect-fdroid/repo> |
| fdroiddata (main F-Droid repo) | Blocked, §5 | — |

Package `org.beuconnect.app`, versionCode 2 / 1.1.0, APK signer SHA-256
`7f6a14260ebc1fb7fd06cb34e5dcf49caa489674a268ff04bc72265596057076`.

## 1. The self-hosted repository

| Piece | Value |
|---|---|
| Repository URL | `https://pritkr.github.io/beuconnect-fdroid/repo` |
| Landing page | `https://pritkr.github.io/beuconnect-fdroid/` |
| Repo site source | <https://github.com/pritkr/beuconnect-fdroid> |
| Index signing key SHA-256 | `7B:3F:3E:CE:F7:C6:FC:EA:99:D3:C6:34:E8:EA:71:5E:18:0E:A8:8D:A3:2F:57:2A:62:BE:AC:49:BA:8E:69:8E` |
| Generated by | `scripts/publish-fdroid.sh` |

The repository is a static directory of a signed index plus the APK, served by
GitHub Pages. F-Droid clients verify the index against the repo key, then verify
the APK against the signer allowed in the metadata.

The APK is the same artifact as the GitHub release. Android upgrades an installed
BEUConnect in place because both carry the release key; the debug-signed
development builds install only after an uninstall.

## 2. Keys

Two independent keys. Do not merge them.

| Key | Signs | Path |
|---|---|---|
| Release key | the APK | `~/.config/beuconnect/beuconnect-release.jks`, secrets in `signing.env` |
| Repo key | the index, `entry.jar` | `~/.config/beuconnect/fdroid-repo.jks`, alias `fdroidrepo` |

`fdroid-signing.env` holds `FDROID_KEYSTORE`, `FDROID_KEY_ALIAS`,
`FDROID_KEY_PASS` and `FDROID_KEY_DNAME`; the publish script reads it and writes
a mode-600 `config.yml` in a scratch directory. Neither file is in this
repository. Back both up offline — losing the repo key forces every client to
remove and re-add the repository, losing the release key blocks every future
update.

`entry.jar` is signed SHA-256/SHA-384. `index-v1.jar` carries a SHA-1 signature
because fdroidserver keeps the legacy index for old clients; that is by design,
not a defect to fix.

## 3. Publishing a release

```sh
# 1. version: nsh.json `version` and `build`, then a changelog entry
$EDITOR nsh.json
$EDITOR fastlane/metadata/android/en-US/changelogs/<build>.txt

# 2. release: checks, tests, the slim arm64 APK, size gate, verification
./scripts/release.sh

# 3. publish the APK as a GitHub release, then build the repo index
gh release create "v$(bun -e 'console.log(require("./nsh.json").version)')" \
  dist/BEUConnect-*.apk#BEUConnect.apk --notes-file /tmp/notes.md
./scripts/publish-fdroid.sh v1.2.0 ../beuconnect-fdroid
git -C ../beuconnect-fdroid commit -am "BEUConnect 1.2.0" && git -C ../beuconnect-fdroid push
```

`publish-fdroid.sh` downloads the release APK, refuses it unless `apksigner`
reports the signer in `fdroid/metadata/org.beuconnect.app.yml`
(`AllowedAPKSigningKeys`), runs `fdroid update --clean`, restores the repository
icon that `--clean` replaces with a placeholder, and writes `../beuconnect-fdroid/repo`.

GitHub Pages rebuilds within a minute; the index URL is
`repo/index-v2.json` (also `index-v1.jar`, `entry.jar`, `index-v1.json`).

## 4. Installing

In the F-Droid client: **Settings → Repositories → Add repository**, then the URL
above. The client fetches the index, shows the fingerprint, and offers BEUConnect
1.1.0. The landing page also carries an `fdroidrepos://` link that opens the
client directly.

Without F-Droid, the APK at `repo/org.beuconnect.app_2.apk` installs the same way
as the GitHub release asset.

## 5. Official F-Droid: what blocks it

fdroiddata builds every app inside a Debian container with no network, from a
recipe in the metadata `Builds:` block, and may only use binary dependencies that
come from a trusted build (Debian, Maven Central, and similar) or that the recipe
builds itself.

BEUConnect is a NativeShell app. Its Android host is produced from
`~/.nsh/embed/android/nsh.aar` plus a prebuilt `nsh` CLI (`~/.nsh/bin/nsh`) that
the app bundles into the APK. Those binaries come from the `nsh` release
tarball, which is not a trusted binary source under that policy, and the app has
no build without them.

Unblocking it means one of:

1. **Build NativeShell inside the recipe.** `longbridge/nsh` (Apache-2.0, tag
   `v0.3.0`) is a Rust workspace; the recipe would need a `cargo` stage with
   vendored crates, producing `nsh` and `nsh.aar` before
   `scripts/build-android-host.sh` runs. The bundler step of that build
   (`scripts/bundle-android.sh`, Bun) also has to be reduced to something the
   container can run offline.
2. **Get `nsh` into Debian or a comparable trusted build** and pin it by hash.
3. **Ship a non-NativeShell Android build** for F-Droid, which would be a second
   app implementation and is not planned.

Until then, do not open the fdroiddata merge request: a recipe that cannot build
is rejected, and the repository metadata here is for the self-hosted repo only.
